# 前端规划：帮助用户「回测 + 看买卖点」

> 目标：让一个不懂缠论的用户，能在 **3 次点击内** 回答两个问题：
> 1. 缠论在这只票 / 这段时间上**到底准不准**（可证伪，不是听我说）
> 2. **现在该不该买卖**（最新信号 + 依据）
>
> 写作原则：本文件里的每条"现状"都来自实际读代码 / 实测，不写没验证过的。

`/chanlun` 已 redirect 到 `/learn?tab=analysis`（router.ts:23 实测）。

### 关键服务能力（实测确认）

- `/api/v1/chanlun/analyze`（POST）—— 返回 `mmds / bis / zss / xds / fractals / macd`
  - ⚠️ **market 必须大写** `^(SZ|SH|BJ)$`，传小写 → **422**（实测 curl 复现）
  - 750 根日线响应约 3~6s，含 14~15 个 mmd
- `/api/v1/bars?market=sh&code=...&category=DAY&count=N` —— **小写**即可（与上面不同，别混用）
- `/api/v1/backtest/run` —— 单标的回测；`/backtest/run/async` + `/backtest/tasks/{id}` 异步
- **没有** 多标的批量回测接口（只有 `/diagnosis/multi-stock`，那是诊断不是回测）

### 已验证的模型正确性口径（scripts/verify_chanlun_correctness.py）

三层判据，越往上越硬：
- **L1 方向对不对**：买点后 N 根真涨？卖点后真跌？
- **L2 胜过随机吗**：与同数量随机入场对照（固定种子，可复现）
- **L3 显著吗**：配对 t 检验 + **Bonferroni 多重比较校正**（测 8 类型×3 档=24 次，阈值收紧到 |t|>3.08）

第 3 层是现有前端**完全没有**的 —— 页面只显示数字，不显示"这个数字可不可信"。

## 三、具体改造清单（按优先级）

### P0 — 让「准不准」可证伪（最高价值）

现状问题：表格给了一堆百分比，但用户无法判断这些数字**是不是运气**。

改造：在 `/signal-check` 的统计表加两列：

| 新增列 | 含义 | 为什么必须有 |
|---|---|---|
| **样本数** | 该类信号总次数 | n=1 的"100% 命中率"毫无意义，必须暴露 |
| **可信度** | 通过 Bonferroni 校正的显著性检验才打 ✅ | 24 次检验里必然有 ~1 次"显著"是运气 |

### ✅ P0 已完成（2026-10-10）

- 已抽出**唯一口径** `src/easy_tdx/backtest/signal_stats.py`
  （`is_buy_type` / `forward` / `random_baseline` / `paired_t` /
  `bonferroni_crit` / `evaluate_type`）
- 已新增接口 `POST /api/v1/chanlun/signal-stats`（大写 market，与
  `analyze` 一致的 `start_date`/`end_date`）
- 前端 `/signal-check` 表格已加**样本数**列，结论列改为三档显著性判定，
  并展示 Bonferroni 阈值
- **审计脚本、接口、前端三处共用同一份统计实现**（有单测锁住，见
  `tests/unit/test_signal_stats_contract.py`，含牙齿）
- 另有源码守门 `scripts/check_mmd_type_guard.py`（已进 CI）
  ，静态扫描禁止再写 `endswith("buy")` 这类判定

### P1 — 回测页加「多标的」能力

现状：`/backtest/run` 只能单标的。用户想验证"模型对不对"，50 只的统计比 1 只有说服力得多。

改造：
- 新增 `POST /api/v1/backtest/run/multi`（异步，复用 `/backtest/run/async` 的任务机制）
- 前端：回测页加「批量」tab，选多只 → 后台跑 → 出**汇总表**（胜率、平均超额、显著性）
- 性能：单只日线缠论约 3~6s，50 只约 3~5 分钟，必须异步 + 进度条

### P2 — 图上可交互核对（用户最想要但也是最容易做假的）

现状：ChanlunChart 已能画 mmd 标注，但用户无法**逐一点开**核对。

改造：
- 点图上/列表里的信号 → 高亮该点 + 显示**它之后 N 根的实际走势**（小图或文字）
- 显示**缠论判据原文**（`msg` 字段已有，如 `3卖: 跌破中枢下沿后反抽不破，高点=1271.50 < zd=1280.34`）
  —— 让用户能自己核对"这个点按缠论到底该不该标"

⚠️ 这个功能的价值**依赖缠论本身正确**。按 §7 保真度审计：
  - **3买/3卖** = 原文级可信，可以放心给用户看
  - **1买/2买** = 尚未做修复前后对照，**展示时应标注"待验证"**

### P3 — 统一「市场状态」提示

用户关心"牛熊震荡能不能持续盈利"。回测结果必须**带上这段行情本身涨了多少**：
- 每个回测结果旁显示「同期买入持有 +X%」
- 并给出信号超额，而不是只给绝对收益
（否则牛市里随便买都赚，用户会误判成模型准）

## 2026-10-10 补记：自选股票 + 历史区间 + 区间套（已实测打通）

用户要求：「选某只股票和某个历史时间区间，标记买卖点中枢，查看之后 K 线，
并能通过区间套看更精准的买卖点」。实测打通，过程中修掉 4 个真 bug：

### 修掉的 bug

1. **`fetchBars` 从不把日期发给服务端**
   `fetchBarsDirect` 只做本地分页翻取，而 TDX 协议取数**锚定最新 bar**，
   请求 2024 年窗口时翻页拿到的全是 2026 年数据，再被本地 `applyBarsWindow`
   过滤 ⇒ 结果为空。修法：给 `/bars` 带上 `start_date`/`end_date`，
   让服务端 `fetch_bars_range` 分页直达。

2. **切到「自定义区间」时日期为空就发请求**
   `watch` 在 `preset` 变成 `custom` 那一刻就触发 `load()`，此时两个日期
   仍是空 ⇒ 拉回「最新 3000 根」，且这次请求**最后完成**、覆盖掉后面正确
   的窗口请求。修法：`customReady`（两个日期都填了）才 `load()`。

3. **`/chanlun/multi-level` 完全忽略 `start_date`/`end_date`**
   它继承了该字段却从不使用，始终走 `fetch_qfq_klines` 从最新往回取。
   后果：历史窗口下次级别为空 ⇒ `low_bi_count=0` ⇒ 区间套**全 false**。
   修法：与 `/analyze` 同口径，给了日期就走 `fetch_bars_range`。

4. **区间套请求 32s，超过浏览器 fetch 30s 上限 ⇒ 前端必然 failed to fetch**
   `ChanlunAnalyser.process_klines` 是**超线性**的（实测 500 根 0.6s、
   3000 根 16.1s、3976 根 29.5s，≈ n^1.6），而 multi-level 要跑 high + low
   两份。修法：低级别截断到 `LOW_MAX_BARS=3000`（32s → 17s，且 6/7 条
   区间套确认结果不变 —— 窗口外的历史不参与确认）。

### 实测结果（600519，2024-09-02 ~ 2026-10-09，506 根日线 + 30min 次级别）

- 自定义区间：✅ `600519 · 日线 · 2024-09-02 ~ 2026-10-09 · 共 506 根`
- 区间套列：✅ `✅ 3/3`、`✅ 1/1`，共 12 个信号被次级别确认
- 数据边界提示：窗口早于 30min 数据起点（2024-09-13）时，
  显示「没有低周期数据可做区间套」，区分**数据覆盖不到**与**模型判断失败**

### 数据边界（必须让用户看见）

30min 真实数据**只能回溯到 2024-09-13**（实测 3976 条）。选更早的窗口
区间套必然全 false —— 这不是模型失效，是数据覆盖不到。
